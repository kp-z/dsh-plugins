# DECISIONS · 为什么是这样

每条都写清「被否决的方案」——否则下一个人会把它重做一遍。

## D1 一个角色同一时刻只有一张嘴

- **采纳**：一个角色至多一个活会话；换 = 归档 + 新开。
- **否决**：一个人多个活会话（工作号/私人号/旁观号），配 primary/secondary/observer 路由。
- **因为**：「多个活会话」是聊天软件的习惯，不是人的习惯；两个活会话会让同一个人在两份上下文里各说一套，
  回放时说不清哪句算数。而它换来的只是「语气不同」——用 channel 注入就能做到。
- **副作用**：路由规则（谁能代表他发言、谁能看到什么）整套删掉，净减代码。

## D2 注入是分节的 bundle，不是一个 prompt 字符串

- **采纳**：ContextBundle = provider 列表的产物，每节带 source。
- **否决**：一个模板字符串，按场景拼。
- **因为**：整段 prompt 没法单测、没法局部替换、坏了定位不到哪层；加一层要改调用方。

## D3 角色与会话彻底解耦

- **采纳**：Character 只存「不随会话变、不随 tick 变」的事实；会话每次开口向世界要 bundle。
- **否决**：把 persona 塞进会话；或把「当前在哪、在干嘛」存进角色。
- **因为**：前者让换会话 = 换人；后者让角色变成状态快照的别名，回放必然错。

## D4 短信/对话都过世界，不直连

- **采纳**：A 说 → 世界记 → 世界决定投 → 投给 B；线程与记录都属于世界。
- **否决**：A 直接调 B 的 send_message。
- **因为**：直连绕过「谁在场、谁有话说、花了多少钱」，且回放查不到「这句是回什么说的」。

## D5 短信 receive 与 deliver 分离

- **采纳**：receive 立刻回执并入队；deliver(tick) 才调模型。
- **否决**：receive 里直接等模型回复。
- **因为**：「他在走路，过会儿才回」如果靠超时表达，玩家看到的是「消息石沉大海」。

## D6 防环写成规则，不写进提示词

- **采纳**：maxHop（默认 2）+ 每 tick 预算，超了抛能照着改的错。
- **否决**：在 prompt 里写「不要一直聊下去」。
- **因为**：模型每次只看到当前一句，不会自己停；这本来该规则裁决。

## D7 预算是共享对象，按 tick 计

- **采纳**：Budget 一个对象，四个入口共用；并发 Guard 满了就拒、不排队。
- **否决**：每个入口各自限流；或排队等待。
- **因为**：各自限流的真实上限永远「加起来不知道多少」；排队把「反应慢」变成「过很久突然说一句莫名其妙的话」。
  按 tick 是因为一次往返在同一 tick 内完成，按「对话」计看不见成本。

## D8 记忆有损

- **采纳**：最近 6 条 × 每条 80 字，时间正序，标注说话人。
- **否决**：整段线程注入。
- **因为**：上下文越长，模型越爱主动引用没人问的旧细节，人会显得絮叨。

## D9 前端零改动，游戏性是契约

- **采纳**：只做后端供对；emit 的形状严格照前端校验；移动有判别式单测。
- **否决**：改前端修问题。
- **因为**：前端是已发行、已调过手感的引擎；改一个字节就是另一个游戏，而且无法回滚。
- **守门**：verify.mjs 逐文件 sha256（2401 个文件）。

## D10 投影层不算路径

- **采纳**：PresenceView 只做「按步长逼近目标」+ 取整输出。
- **否决**：服务端实现一套寻路。
- **因为**：前端已有 EasyStar；服务端再来一套就有两份「怎么走」，最容易腐化成不一致。
