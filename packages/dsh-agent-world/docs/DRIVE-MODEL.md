
# 驱动模型：DSH 会话怎么和这座城连起来

## 一句话

**城市是 DSH 会话组的空间视图，会话是城市的决策来源。**
不是"再做一个世界"，而是把已有的 agent 团队换一种看得见的方式呈现，同时把"人怎么介入"变成空间化的操作。

## 三条线，别混在一起

| 线 | 方向 | 载体 | 频率 |
| --- | --- | --- | --- |
| 状态线 | 会话 → 城市 | session 事件 → role presence（在哪、在干嘛、忙不忙） | 秒级，纯映射，零模型调用 |
| 对话线 | 玩家 ↔ 会话 | 送信/电话面板 → send_message → 气泡与短信 | 人工触发，每条一次模型调用 |
| 动作线 | 城市 → 会话 | 世界给角色派活/发事件 → 会话决定怎么做 → 命令回世界 | 事件驱动，低频 |

三条线分开的理由很实际：状态线是**便宜的**（只读映射），对话线是**用户主动的**（值这个钱），
动作线是**最贵的**（要模型判断）。混在一起就会出现"每 tick 都在思考"的账单。

## 驱动模型：世界确定性，AI 只在分叉点介入

~~~
tick（10Hz，纯确定性）
  ├─ 移动 / 日程 / 状态衰减 / 碰撞      ← 不需要模型
  └─ 到达分叉点时才抛事件：
       · 日程切换（起床→上班）
       · 遇到另一个角色（要不要搭话）
       · 收到玩家短信
       · 任务被派下来 / 卡住了
            ↓
       DSH 会话（一次 turn）
            ↓
       产出**命令**（不是状态）：move / say / act / give_up
            ↓
       世界校验并入队 → 下一 tick 生效 → 写 journal → 派生视觉帧
~~~

铁律三条：

1. **世界是唯一真源**。会话只能提交命令，不能改状态；命令要么被接受、要么带着原因被拒。
2. **命令必须可回放**。所有变更进 journal，给定 tick 能重放出同一画面——这也是前端断线重连的前提。
3. **一次 turn 只做一件事**。会话不是"持续思考的脑子"，是"被叫到就问一次的人"。

## 状态线：会话就是角色，但别按 tick 同步

- 一个 DSH 会话 ↔ 一个角色（沿用现有的 boundAgentId 绑定）。
- 角色在城里显示什么，只取决于**会话的粗粒度状态**：是否 running、当前在做什么（工具名→动作）、最近一条消息（气泡）。
- 投影规则集中在适配层一处：session event → presence 的 (place, x, y, facing, 忙/闲, 当前动作)。
- **不要在会话 turn 中间逐字同步**。前端每 30 秒更新一次"他在干嘛"足够；位置沿用世界的确定性移动。

## 对话线：手机面板就是聊天窗口

这是这套前端最值钱的地方——它自带短信、通话、通讯录的完整 UI。

- 在城市里点一个角色 → 打开手机 → 发短信 = 对该会话 send_message（带世界上下文：他在哪、在干嘛、你们的关系）。
- 回复走 SSE 回到手机面板，同时角色头顶冒气泡。
- 冷启动成本控制：**只有被点开的角色才唤醒会话**，其余角色在世界里跑确定性日程。

## 动作线：把工单变成"他去上班"

现有 agent-world 的 dispatch/report 工具不用改，改的是**呈现**：

- 派单 → 世界里生成"工作点"（place + 坐标）→ 角色走过去 → 到达后进入 working 状态 → 完成后回到常态。
- 会话看到的工具结果里带"你正在公司三楼的工位"，它说的每句话就自然带上了空间感。
- 这才是"城市"和"工单"真正合上的地方：**任务在空间上有位置**。

## 落地顺序（每步都能单独验收）

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| S1 状态线 | session → presence 投影；角色会跟着真实会话的忙碌变化 | 起 2 个会话，城市里两个人的状态跟着变 |
| S2 对话线 | 手机面板打通 send_message，回复落成气泡+短信 | 给角色发一句，他能回，且知道自己在哪 |
| S3 动作线 | 派单 → 走到工位 → working → 完成 | 派一张单，能在城市里看完整条路径 |
| S4 视觉管道 | 命令执行 → visual_timeline → HUD 播帧 | HUD 里的城市动起来（当前卡点） |

## 陷阱

- **别让会话写状态**：一旦允许，回放与并发都会坏，而且坏得极难查。
- **别按 tick 调模型**：10Hz × 24 人 = 每秒 240 次，这不是钱的问题，是延迟的问题。
- **别把提示词塞进前端**：前端是编译产物，提示词属于世界配置。
- **别让状态线依赖模型**：忙闲、位置、动作必须能在模型挂掉时仍然正确。


## 附：绑定粒度（世界 ↔ 会话 ↔ 角色）

### 结论

**一个世界不再是一个会话。** 世界是**服务**（常驻、无会话身份），会话挂在**角色**上。
但这个绑定有三处必须说清楚，否则会做成"24 个会话常驻"的账单灾难。

### 三条修正

**一、世界是服务，不是会话。**
现在 world ↔ session 的一对一是历史包袱：世界需要的是时钟、tick、journal、存档，
这些都不是会话能提供的东西。世界的身份是 world_id，会话只是**住在里面的某个居民**。
队长会话可以保留，但它的角色是"导演/派单者"，不是世界本身。

**二、绑定 ≠ 常驻。**
"一个角色绑一个会话"说的是**身份**（有记忆、有历史、有工具权限），
不是"这个会话一直活着在思考"。正确形态是：

~~~
角色 → sessionId（长期不变，代表这个人）
     → 平时 dormant（不跑 turn，零 token）
     → 事件到达时唤醒一次（一次 turn = 一个决定）
     → 产出命令 → 回到 dormant
~~~

反例是"每个角色一个常驻循环"：上下文越来越长、账单线性增长、而且 24 个人的思考会互相打架。
DSH 的会话本来就适合"叫到才醒"——send_message 一次就是一次 turn。

**三、串行是世界的责任，不是会话的自律。**
前端一个角色只显示一个动作，所以：
- 世界给每个角色一个**任务队列**（当前动作 + 待办）；
- 有动作在跑时，新命令要么排队、要么带原因拒绝（"你正在去公司的路上"）；
- 会话不需要知道"我不能同时做两件事"，它只需要收到一句拒绝理由。

把这条放在世界里，回放才成立；放在提示词里，模型迟早会同时做三件事。

### 于是模型长这样

| 层 | 身份 | 生命周期 | 成本 |
| --- | --- | --- | --- |
| 世界 | world_id | 常驻，落盘 | 0 |
| 角色 | role_id | 常驻，世界里的一条记录 | 0 |
| 会话 | sessionId（挂在角色上，可为空） | 长期存在，平时 dormant | 唤醒才计费 |
| 任务 | task_id | 队列里流动，做完归档 | 0 |

关键性质：**角色可以没有会话**。没有会话的角色就是 NPC：日程确定、行为模板化、成本为零。
于是"一座城 24 个人，其中 3 个是你的 agent"是自然成立的——
真实感来自 NPC 的密度，成本只花在你真正关心的那几个人身上。

### 任务怎么流转（"下一个任务"的节奏）

~~~
1. 世界派一个任务给角色 → 入队（不会打断当前动作）
2. 当前动作做完 → 世界唤醒该角色的会话一次：
     "你刚送完货。现在 14:20，你在便利店，手上有 1 个待办（取货），体力 62%。"
3. 会话回答：接受 / 拒绝并给理由 / 换一种做法
4. 世界把回答翻译成命令 → 下一个动作 → 回到步骤 2
~~~

这就是"完成任务再领下一个"的自然节奏：**由世界的队列驱动，不由模型轮询**。

### 代码上要改的三处

| 现在 | 改成 |
| --- | --- |
| state.activateSession(sessionId) 切世界 | 世界按 world_id 常驻；会话只做角色绑定 |
| world.agents[i].boundAgentId（一个绑定） | role.sessionId 可空 + 一张 绑定表（便于换人/解绑） |
| 命令直接生效 | 每个角色一个动作队列；世界校验后排队，忙时拒绝并给原因 |
