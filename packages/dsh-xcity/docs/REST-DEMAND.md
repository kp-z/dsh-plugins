# REST-DEMAND："歇一会儿"到底吃了多少座位

> **一句话**：9.2 座/天不存在——那是把 `world.activities` 这个**环形缓冲（≈4.94 天）**的总座位-分钟当成一天，
> 再除以 1440 得到的。按天折算，"歇一会儿"只占 **1.81 座**（10 座的 18%），白天峰值 4.7 座；
> **打满 10 座的是夜里 04:00–07:00 的睡觉，不是歇脚**。参数（阈值/时长/回补）是健康的，不该再为"歇一会儿"加座位。
>
> 数据出处：测试宿主 `127.0.0.1:3190`，56 人，只读。
> A 快照 = 08:39 / tick **200774**（10 张休息位，commit 8f44e71 之前）；
> B 快照 = 08:56 / tick **206500**（22 张休息位，R531 已提交）。**没有改任何代码**。

## 0. 结论（四条，按重要性）

1. **口径错**：`13290 tick` 是环形缓冲里 rest 活动的**全部**座位-分钟，不是一天。除以窗口 4.94 天再除 1440
   是 **1.87 座**（本快照 12931 → 1.81，逐 tick 扫线）。见第 1 节。
2. **白天不饱和**：休息位白天峰值 4.7 张（13 点、16 点），上午 0–2.8 张；"十张全满"的 tick 占比 ≤7%，
   只出现在 13–16 点零星的几分钟。见第 2 节表 2。
3. **夜里才是瓶颈**：04:00–07:00 三小时里 **100% 的 tick 十张全满**，使用者是 `sleep`（≈10 座），`rest` 夜间 ≈0。
   根因是 `SLEEP_TICKS = 480` 与夜间窗口 480 分钟**等长**——一张床一晚只能服务一个人。见第 4 节。
4. **歇一会儿的参数是健康的**：一次 60 分钟回 `(0.35−0.045)×60 = +18.3`，稳态间隔 `18.3/0.065 ≈ 281` 分钟
   （4.7 小时工作 / 6.8 小时闲置）。不是"歇一小时只回一点"。**阈值改了不省座位**（间隔与阈值无关，见第 5 节）。

## 1. 口径：`activities` 不是一天，是 24 条/人

`src/sim/activity.ts:31,34,37-39`：环容量 = `max(64, 24 × 人数)`。56 人 → **1344 条已完成活动**。
所以窗口长度由"活动产生的速度"决定，不由时间决定：

| | A（10 座） | B（22 座） |
|---|---|---|
| 环内活动条数 | 1352（1344 已完成 + 8 active） | 1365 |
| 窗口 tick 区间 | 193660–200774 | 201582–206500 |
| **窗口长度** | **7114 tick = 4.94 游戏日** | **4918 tick = 3.42 游戏日** |

复算：`rest 座位-分钟 = 2609 / 天`（= 12931 总 tick ÷ 4.94 天）→ `2609/1440 = 1.81` 座。

任务卡的 `13290` 与本快照的 `12931` 是**同一个量**：环里 rest 活动的座位-分钟总和。它随快照漂移（环在滚动），
这本身就说明它不是一个"每天"的量：`12931 / 1440 = 8.98`（≈9.2），等于**把 4.94 天当成一天**。

> 同一处错误也进了 `docs/SEATING-CAPACITY.md:185`（"rest 需 9.22 座"）：`9.22/4.94 = 1.87`，与实测 1.81 吻合——
> 它也是整环总数 ÷ 1440。sleep 5.33 / meal 2.19 与本次快照对不上（应是另一个时刻的环），但同样没有除以窗口天数。
> **定容方向没错（休息位确实不够），定容幅度错了**：`16.7` 这个需求峰值里，rest 的真实份额是 1.9 而不是 9.2。

## 3. 能量账：为什么整个世界卡在 p50 = 11.6

A 世界实测需求分布：**energy p10/p50/p90 = 0 / 11.6 / 97.9（均值 28.3）**，饥饿 p50 = **0**，33 人"站着且什么都没在做"。

每人每天的能量收支（用实测活动分钟数 × `needs.ts` 的速率，已含 −0.045 基线）：

| 项 | 分钟/人/天 | 净速率/分钟 | 能量 |
|---|---|---|---|
| 干活 + 学习 | 103 | −0.065 | −6.7 |
| 聊天 | 37 | −0.045 | −1.7 |
| 吃饭 | 54 | +0.005 | +0.3 |
| **歇一会儿** | 47 | **+0.305** | **+14.3** |
| 睡觉 | 86 | +0.305 | +26.2 |
| 空闲/走动（1113 分钟） | 1113 | −0.045 | −50.1 |
| **合计** | | | **−17.7 / 人 / 天** |

也就是说：这个世界的"歇一会儿"没有失灵，它每天确实回了 +14.3；**缺口在睡觉**——每人每天只睡到 86 分钟，
而补上 −17.7 只要每天多睡 `17.7/0.305 ≈ 58` 分钟，即 **86 → 144 分钟**就能平账。原因不是参数，是床位（见下）。

## 4. 供给还是需求：分两班看，两班结论相反

| | 白天 07:00–23:00 | 夜里 23:00–07:00 |
|---|---|---|
| rest 占用 | 2.5–4.7 座 / 10 → **供给富余** | ≈0 → 不参与 |
| sleep 占用 | 0–3.3 座 | 04:00–07:00 **10/10，100% 打满** |
| 判定 | **需求没打满供给** | **需求远超供给** |

夜里的算术（这才是"该加座位"的部分）：

- 想睡的人 = 全人口 56（`life.ts:423` 的夜间分支**不看 energy**，夜里人人想睡）；
- 一夜的床位-分钟需求 = 56 × 480 = **26880**（= 18.7 座等效/天）；
- 供给 = 10 座 × 480 = 4800 → **一晚上只服务 10 个人**（数据印证：4.94 天里只有 18 个不同的人睡到过觉，每晚 10.1 次 sleep）；
- **`SLEEP_TICKS(480) == 夜间窗口(480)` ⇒ 每张床每晚只能翻台 1 次**。床位需求 = 人数，调阈值/回补都改不了这条。

同时注意另一个反向事实：`no-rest-station`（`life.ts:434`，"累了但一个空位都没有"）累计 **55920 次**，
占全部决策 3.3%（1,709,310 次决策 / 23,674 tick）。这些**全部是白天的瞬时满座**——夜里的人走的是
sleep 分支（`life.ts:423` 在 energy 判定之前 return），根本进不到这一档。所以它既不是常态，也不代表夜间缺床。

### 表 3 — A/B 对照（同一世界，只多了 12 张休息位）

**这张表是本文最重要的证据**：
1. 休息位 10→22 让"歇一会儿"从 43.5 涨到 46.6 次/天——**真需求只有 ~2 座，扩充对歇脚没有杠杆**；
2. 多出来的 1.92 座是"**没工位，坐休息区等**"——工位 19 张 vs 56 人，短缺漏进了休息区；
3. 能量 p50 从 11.6 到 54.8，**不是因为歇得更多，是因为睡觉的人从 10 个变成 22 个**。

> B 世界只跑了 3.42 天且含重启，能量收支算出 +37.2/人/天（仍在回补，不是稳态），所以 B 的数值只能看方向，不能当稳态基线。

## 5. 该加座位还是调参数：改哪一行

| 想达到 | 改哪里 | 从 → 到 | 预期（可算） | 代价 |
|---|---|---|---|---|
| **让 22 张床在夜里服务更多人**（首选） | `src/sim/life.ts:56` `SLEEP_TICKS` | 480 → **300** | 每床每晚 1.6 人 → 22 座服务 ≈35 人（现 22） | 单改无效，必须配下一行 |
| 同上（必需配套） | `src/sim/life.ts:423` 夜间分支 | 无条件 → `needs.energy < 60` | 睡够的人不再占床，翻台才生效 | 语义微调：夜里可能有人不睡 |
| 保持睡满的体感（可选配套） | `src/sim/needs.ts:50` `PURPOSE_RATE.sleep.energy` | 0.35 → **0.50** | 300 × (0.50−0.045) = **+136** ≈ 现在的 480 × 0.305 = +146 | 一行常数 |
| 只加床（不推荐先做） | `office.ts` 再加 34 座（≈6 排） | 22 → **56** | 夜里全员有床 | 白天 22 座已有 65% 空置、其中一半是等工位；收益只在夜间 8 小时 |
| 想让白天更省座位（可选，非必需） | `src/sim/needs.ts:51` `PURPOSE_RATE.rest.energy` | 0.35 → **0.70** | 单次 +39（30→69），稳态间隔 281→600 分钟，歇脚次数≈减半，rest 座位 1.8 → **≈1.0** | 离"人真的会累"更远；现在不缺座位，别先动 |
| **不要动** | `src/sim/life.ts:50` `ENERGY_LOW` | 30 → 20 | **稳态间隔不变**（= 单次回补 ÷ 消耗速率 = 18.3/0.065，与阈值无关），只让第一次歇更晚 | 纯无效改动 |
| 真正的漏点（不属本文范围） | 工位：19 座 vs 56 人 | 19 → 24~32 | B 世界里 60.9 次/天、**1.92 座**被"等工位"吃掉 | 见 `docs/SEATING-CAPACITY.md` |

**结论：**
- 对"歇一会儿"：**不用加座位，也不用调参数**——白天 10 张座位只用 1.8–4.7 张；
- 要加就加**夜里能躺下的位置**，而且更便宜的做法是让床翻台（`SLEEP_TICKS` 480→300 + 夜间分支加 energy 条件），
  不是把床从 22 堆到 56；
- 休息区被"等工位的人"占掉的那 1.92 座，是**工位短缺**的症状，扩休息位只会把症状藏起来。

## 6. 读这个宿主时的三个口径陷阱

1. **`activities` 是环形缓冲**（24 条/人），任何"除以 1440"的统计必须先除以窗口天数（本次 4.94 / 3.42 天）。
   窗口长度 = `条数 ÷ 活动产出速率`，人越多窗口越短。
2. **`intentStats` 的 `ok` ≠ 有活干**：`waitOption` 也会给意图（`life.ts:377`、`:417`、`:427`），
   所以夜里抢不到床的人被记成 `ok`；`night-no-rest`/`hungry-no-breakroom` 只在"世界上一个这类站点都没有"时才 +1，
   **恒 0 不代表没人缺**（A 世界夜里 46 人抢不到床，计数器是 0）。
3. **"等"的痕迹不统一**：抢不到座位时，意图在 `step.ts:633` 被丢弃 → 不留活动；一旦等到座位（B 世界 208 条）
   就变成一条 `purpose=rest`、时长 30–60 的"假歇脚"。统计 `rest` 必须按 `trigger.text` 拆开，否则会把排队算成休息。

## 7. 复现

```sh
# 1) 取快照（只读）
curl -s http://127.0.0.1:3190/agent-world/api/world -o /tmp/w.json

# 2) 窗口长度 / 每个 purpose 的座位-分钟（关键：除以 span，不是 1440）
node -e '
const w = JSON.parse(require("fs").readFileSync("/tmp/w.json","utf8")).world;
const a = w.activities, span = w.tick - Math.min(...a.map(x=>x.startedAt));
const dur = x => Math.max(0,(x.endedAt ?? Math.min(x.endsAt,w.tick)) - x.startedAt);
console.log("window days", (span/1440).toFixed(2), "ring cap", Math.max(64,24*w.agents.length));
for (const p of ["rest","meal","sleep"]) {
  const l = a.filter(x=>x.purpose===p);
  console.log(p, "acts/day", (l.length/(span/1440)).toFixed(1),
    "avgDur", (l.reduce((s,x)=>s+dur(x),0)/Math.max(1,l.length)).toFixed(1),
    "seats", (l.reduce((s,x)=>s+dur(x),0)/span).toFixed(2));
}
const waits = a.filter(x=>(x.trigger?.text??"").includes("等着"));
console.log("wait-typed rest", waits.length);'
```
